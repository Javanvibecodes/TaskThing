# Local synchronization protocol

This document describes the current desktop-hosted protocol. It is an
implementation reference, not a promise of long-term wire compatibility.

## Transport

- HTTP server hosted by the desktop app.
- WebSocket connections handled by the `ws` package.
- Desktop binds the HTTP server to `0.0.0.0` on a dynamically selected
  available port, with the chosen port stored in desktop settings.
- Current mobile configuration allows cleartext local traffic.
- The transport is not encrypted; do not expose it to untrusted networks.

## Authentication and pairing

The WebSocket upgrade accepts either the desktop's persistent pairing token
or the current six-digit pairing code.

1. The desktop displays a randomly generated six-digit code.
2. A mobile client connects with the code.
3. The server compares credentials using a constant-time comparison.
4. A successful code-based connection receives a `PAIR_ACCEPTED` message
   containing the persistent reconnect token.
5. The server rotates the pairing code immediately after successful use.
6. The phone stores the reconnect token locally for later connections.

Failed authentication is rate limited per remote address: five failures
within a 60-second window cause subsequent attempts from that address to be
rejected with HTTP 429 until the window resets.

The current implementation does not attach a time-based expiry to the
displayed code. It is single-use and rotated on success, but should not be
described as expiring after a fixed duration.

## Message envelope

WebSocket messages are JSON objects with this general shape:

```json
{
  "type": "MESSAGE_TYPE",
  "payload": {},
  "timestamp": 0
}
```

The timestamp is a Unix time in milliseconds generated by the sender.

## Messages handled by the desktop server

| Type | Purpose |
| --- | --- |
| HELLO | Introduces the mobile device name and platform |
| SYNC_INIT_REQUEST | Requests the current full state snapshot |
| OFFLINE_QUEUE_SYNC | Sends a batch of queued mobile mutations |
| WEBRTC_SIGNAL | Broadcasts signaling payloads to other connected clients |
| Other typed mutations | Applies the mutation handler and broadcasts a fresh snapshot |

## Messages emitted by the desktop server

| Type | Purpose |
| --- | --- |
| WELCOME | Returns desktop name, platform, and active port |
| PAIR_ACCEPTED | Returns the persistent token after code-based pairing |
| STATE_SNAPSHOT | Sends the current full task state |
| WEBRTC_SIGNAL | Relays signaling payloads |

## HTTP endpoints

| Method and path | Current behavior |
| --- | --- |
| GET /ping | Returns basic server status and device metadata; no authentication |
| GET /snapshot?token=... | Returns the task snapshot when the token matches |
| POST /webrtc-signal | Relays a signaling payload; no authentication in current code |
| OPTIONS | Responds to CORS preflight |

The server currently sends permissive CORS headers. Treat the endpoints as
local-network interfaces, not internet-facing APIs.

## Data and conflict behavior

The desktop applies supported mutations to its local store and then
broadcasts a full state snapshot. Offline mobile changes are compacted and
sent as a batch on reconnection. This is not a CRDT or transactional
multi-master protocol. Simultaneous edits, stale clients, and duplicate
mutations may produce surprising results; back up important data.

## Compatibility

No formal protocol version negotiation is currently defined. If message
shapes change, update this document and test desktop/mobile compatibility
together.
